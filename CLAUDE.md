# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js 16 (App Router, React 19, Tailwind 4) frontend in `client/` and an Express 5 API in `server/` (plain ESM JavaScript, no build step). Users have email and password accounts, connect GitHub to them, see the site template and their copies of it, can duplicate a repo (full history) into their own account, and can manage a twinstack-site repo (run its build, content and Claude commands, then commit and open a PR) from the browser. The session cookie only identifies the account. MongoDB (`server/src/db.js`, required at startup) stores accounts (password hash, linked GitHub profile and encrypted token, encrypted Anthropic key) and which repos are copies of the site template. Deployment to a droplet (frontend on `builder.` and API on `api.` subdomains, MongoDB on the same host) is covered in `DEPLOY.md`, and `ecosystem.config.cjs` is the PM2 config. Updates are shipped with `deploy.sh` (see `UPDATING.md`), which `.github/workflows/deploy.yml` runs over SSH after lint and build pass on every push to `master`. It pulls, runs `npm ci`, builds and restarts based on which paths changed (`server/`, `client/`, `ecosystem.config.cjs`), so keep those path rules in sync if the layout changes.

**Before writing any code in `client/`, read `client/AGENTS.md`.** This Next.js version has breaking changes from what you may know; consult `client/node_modules/next/dist/docs/`. For example, route protection lives in `client/src/proxy.ts` (exporting `proxy`), not `middleware.ts`.

## Commands

Node 20.12+ (both packages use `node --env-file-if-exists`).

```bash
npm install          # root; postinstall also installs client/ and server/
npm run dev          # API on :4000 (node --watch --watch-path=src: restarts on any file under src/, preview/inline-edit.js included) and web on :3000, via concurrently
npm run build        # builds client only (server needs no build)
npm run start        # production start of both

npm --prefix client run lint   # ESLint (eslint-config-next); the only lint in the repo
```

There are no tests. Env setup: copy `server/.env.example` → `server/.env` (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `JWT_SECRET`, `MONGODB_URI` and `DATA_ENCRYPTION_KEY` are required; the server throws at startup without them, and exits if MongoDB is unreachable) and `client/.env.example` → `client/.env.local` (`API_URL`). Optional server vars: `WORKSPACES_DIR` (see the site manager section below), `PLATFORM_ANTHROPIC_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `CREDITS_DEMO_PURCHASES` (see Claude credits below), and `TEMPLATE_GITHUB_TOKEN`, `ADMIN_EMAILS`, `RESEND_API_KEY` and `EMAIL_FROM` (see Access below).

## Architecture

**Single origin via rewrites.** The browser only ever talks to Next.js on :3000. `client/next.config.ts` rewrites `/auth/*` and `/api/*` to Express, so the httpOnly `session` cookie is first-party. The GitHub OAuth callback URL therefore points at the *client* (`http://localhost:3000/auth/github/callback`), not the API. `API_URL` is read at build time. `experimental.proxyTimeout` is raised to 10 minutes because duplication can take a long time.

**Accounts and session.** Email and password accounts live in `routes/auth.js` (register, login, logout, with an in-memory failed-login limit) and `passwords.js` (scrypt). Registering and resetting a password both go through emailed 6-digit codes (`server/src/email-codes.js`: `newCode`, `sendRefusal`, `checkCode`; records in `db.js` by kind, `saveCodeRecord`/`findCodeRecord`/`recordWrongCode`/`deleteCodeRecord`). A request emails the code (`sendEmail`) and returns a `token` the browser keeps; the follow-up must bring both. Records (`_id` = email, hashed code and token) are deleted an hour after they're made (TTL). The token means a second request for the same address replaces the first instead of riding on the code the owner receives. Limits: code valid 15 minutes, 5 wrong codes, one send a minute (`retryAfter`, which drives the forms' draining ring) and 5 an hour per address, 10 an hour per IP (in memory, shared). Production refuses both without `RESEND_API_KEY`; in development the code is in the server log.
- Sign-up: `POST /auth/register` keeps the sign-up in `pendingSignups` (with the name and password hash); `POST /auth/register/verify` `{ email, token, code }` creates the account (`emailVerifiedAt`) and the session. Accounts made before this have no `emailVerifiedAt`.
- Password reset (`/forgot-password`, `ForgotPasswordForm.tsx`, linked from the login form): `POST /auth/password/forgot` `{ email }` answers the same whether or not an account uses the address (an unknown one gets a record too, so the waits match, but nothing is sent). `POST /auth/password/reset` `{ email, token, code, password }` saves the password (`setPassword`, which also sets a missing `emailVerifiedAt`), clears the login lockout, signs this browser in and emails a "password changed" notice. The page then asks (`confirmModal`) whether to sign out other devices.
- Sessions: the cookie carries the account's `sessionVersion` (`sv`, 0 when missing). `sessionAccount` in `session.js` (used by `requireAuth` and the GitHub routes' `accountOrLogin`) rejects a cookie whose `sv` isn't the account's current one. `POST /auth/sessions/end-others` raises it (`bumpSessionVersion`) and re-issues the caller's cookie, signing out every other browser. Pass the account's `sessionVersion` to `setSession` whenever signing in.
- The forms share `components/auth/parts.tsx` (the card, code boxes, password field, resend ring, `postJson`). The cookie is a JWE (`dir` + A256GCM, key derived from `JWT_SECRET`) holding only `{ uid }`. `requireAuth` (`session.js`) loads the account from MongoDB on every request. It sets `req.user` to the `publicUser()` shape (`{ id, email, name, admin, access, github | null }`, where `id` is the ObjectId hex) and `req.githubAuth` to the decrypted GitHub token or null. Use `requireGithub` after it on any route that talks to GitHub. Workspace keys, job ownership, Anthropic keys and `siteCopies.userId` all use the account id, never the GitHub id.

**Access (who can create sites).** The template is private and has no collaborators. `users.access` (`status`: `none`/`pending`/`approved`/`denied`, `requestedAt`, `message`, `decidedAt`, `decidedBy`) decides who may use it; `publicUser` reports it as `access` (`{ status, requestedAt }`), and accounts whose email is in `ADMIN_EMAILS` (`config.adminEmails`, `isAdminEmail` in `db.js`) are `admin` and always approved. `connectDb` approves accounts that own a `siteCopies` record and have no `access` yet. `POST /api/access/request` (`routes/access.js`, only from `none`) marks it pending and emails the admins; `/api/admin/access` (GET the list, `listAccessRequests`; POST `/:id` `{ status }`, `setAccessStatus`) is admin-only and emails the account. Approving is a POST from `/admin/access` (`AccessRequests.tsx`), never a link in an email, because mail scanners open links. Email goes through `sendEmail` in `email.js` (Resend's HTTP API, plain text only; without `RESEND_API_KEY` it's printed to the log, and it never throws). In `sites.js`: `hasTemplateAccess(user)` gates duplication (403 `access_required`) and listing the template in `/api/repos` (`withSiteRoles(repos, user)` adds it from `TEMPLATE_GITHUB_TOKEN` when the user can't see it on GitHub), and `templateToken(user, userToken)` is the app's `config.templateToken` for approved accounts (else their own token) for every template read: `duplicateRepo`'s `sourceToken` (clone only; the new repo is created and pushed with the user's token), `readTemplateFile` (the installers) and the site update's commit list and fetch. `appTokenError` turns GitHub refusing the app's token into a plain error, not `reauth_required`, since reconnecting GitHub can't fix it. New sites are public (`private` defaults to false and the create form doesn't offer it). The dashboard's steps are Connect GitHub, Get approved (one click), Create your site.

**Who verifies the session.** Only Express can decrypt the cookie. `client/src/proxy.ts` only checks that the cookie *exists* on `/dashboard/*`, `/sites/*`, `/settings/*`, `/credits/*` and `/admin/*`, and sends guests to `/login?next=…`. `?next` must go through `lib/safe-next.ts`. Server components call `getUser()` in `client/src/lib/session.ts` (`server-only`), which forwards the cookie to `GET /api/me`. It returns null only on 401/403; an API that doesn't answer (restarting, database unreachable) or answers 5xx is tried again twice, then throws `SessionUnavailableError`, which `app/error.tsx` shows with "Try again" (the navbar treats it as no account), so a hiccup never sends a signed-in owner to log in. In the browser, `api()` (`lib/site-api.ts`) tries a GET twice more when the Next.js proxy itself fails (a 5xx without the API's JSON `error`); changes are never repeated. Client components (`Dashboard`, `CreateSite`) call `/api/*` directly from the browser through the rewrite.

**GitHub connection and token refresh.** `/auth/github` → `/auth/github/callback` links GitHub to the logged-in account (`linkGithub`, one GitHub account per app account), and errors redirect to `/dashboard?github_error=…`. `getAccessToken(req)` in `server/src/github.js` refreshes the token when it's within 60s of expiry (only when the OAuth App issues expiring tokens) and saves it back to MongoDB. Any route that calls GitHub should get its token through this function. Any GitHub 401 or refresh failure throws `ReauthRequiredError`, which routes map to `401 { error: "reauth_required" }`. The client treats that code as "Reconnect GitHub" (a link to `/auth/github`).

**Scopes.** `read:user user:email repo workflow`, requested in `server/src/routes/auth.js`. `workflow` is needed to push repos that contain `.github/workflows/*`. The duplicate route rejects older GitHub connections that lack it with a `reauth_required` response.

**Duplication** (`server/src/duplicate.js`). It validates owner and name, then `POST /user/repos`. Next it runs `git clone --bare` of the source into a temp dir and pushes `refs/heads/*` and `refs/tags/*` to the new repo. After that it PATCHes the default branch to match the source, and finally removes the temp dir. If the name already exists and that repo is empty and admin-owned, it is reused, which lets a failed copy be retried. A non-empty repo is never overwritten. The token reaches git only through `GIT_CONFIG_*` env vars (an `http.extraheader`), never through argv or a remote URL; keep it that way. The server host needs `git` installed. Error classes: `DuplicateError` has a user-safe message and HTTP status. `MissingScopeError` maps to reauth. Anything else becomes a 502, with `err.partialRepo` noted if an empty repo was left behind.

**Site manager** (`/sites/[owner]/[repo]`, the README has the user-facing summary). It drives a twinstack-site repo's scripts from the browser:
- `server/src/workspace.js` keeps a persistent clone per user and repo at `WORKSPACES_DIR/<userId>/<owner>/<repo>`. Repo metadata and the `npm ci` lockfile stamp live inside `.git/` so they never appear as changes. It also handles status, diff, discard, commit/push/PR and reset. A per-workspace lock (`acquire`) makes sure only one command or git operation touches a clone at a time.
- `server/src/commands.js` is the only list of runnable commands. Each builds a fixed `node scripts/<x>.js` argv from validated input. There is no shell, and values that start with `-` are rejected. New site commands go here. Scripts get the `jobEnv()` allowlist, never `process.env`, so the GitHub token and server secrets can't reach repo code.
- `server/src/jobs.js` runs commands in memory. The client polls `GET /api/jobs/:id?since=<offset>` (not SSE, so it works through the Next rewrite proxy). Jobs are lost on restart.
- `server/src/site-files.js` reads site data (collections, pages, nav) by parsing files. **Never import repo code into the server process.**
- `server/src/routes/preview.js` serves `dist/` under a signed URL with a CSP sandbox header, and rewrites root-relative `href`/`src`/`url()` into the preview prefix. The client iframe is sandboxed without `allow-same-origin`, so keep both. Site previews (not proposal ones) get `server/src/preview/inline-edit.js` inlined before `</body>`, after the rebase.
- Click-to-edit in the preview (`EditablePreview.tsx` on Edit site, the `home` section; no Claude, no credits): editing is on from the start, and "Stop editing to try links" turns it off, because while it's on the frame's script stops links and buttons inside `<main>` from acting. "Page" (the overview's pages by `address`) and "Edit on site" in Pages (`showOnSite(url)` → `previewTarget` in the context; opening a screen from the menu clears it) send the frame a `go`. A frame load with no `ready` before it means the script never ran (a broken page, such as one cut off by an unclosed `<textarea>`): the editor says editing doesn't work on this page and points to What's changed, where the site check names the problem. The page shown is the AI's open page (`setShownPage` → `assistantContext.page` while on `home`; `describeScreen` says "Edit site, showing <file>", and the quick page edit takes it as the open page; suggestions stay Edit site's). While editing, the frame's script puts "Ask the AI to change this section" on the section under the pointer (`sectionOf`: the outermost `<section>` in `<main>`, else the part of `<main>` it's in, going down while that part is taller than the window; the button lives outside `<main>`, so the click capture leaves it alone, and its text is ASCII-escaped because the script is inlined into any page); pressing it posts `ask-section` (`heading`, `start` from `innerText`, `position`/`count` among its siblings), and the client starts that request in the conversation with `fillDraft` ("On the “About” page (/about.html), change the section headed “Our story” (section 2 of 5): ") for the owner to finish. Editing tells the frame's script (`inline-edit.js`) by `postMessage` to make clicked text inside `<main>` editable (`contenteditable="plaintext-only"`; the nearest non-inline element holding only text and inline parts, so a bold word edits its paragraph). The header and footer keep working, so the menu opens other pages. Enter or clicking away sends `edit` (`path`, `before`/`after` `textContent`, `index`/`count` among `main <tag>` elements with that exact text); Esc restores. The client checks `event.source` is the frame and posts `POST …/pages/text` `{ address, before, after, index, count }` (`editPreviewText` in `server/src/text-edit.js`). That finds the page by its built address (`sitePages`), reads its body as visible text (tags, comments, `{{ }}`, `**`, link syntax and heading markers left out, entities decoded, each character mapped to its source range; `{{ page.title }}`/`{{ page.description }}` read the frontmatter value, so the starter heading edits `title:`), and replaces only the changed characters (common prefix and suffix). When the body doesn't hold the element's whole text, `storedField` looks for one field whose value is exactly that text: the page's own one-line frontmatter (older layouts' `heroHeading`/`heroText`/`kicker`, before `title`/`description`; never `NOT_TEXT` keys), then string values in `site.config.json` and `content/data/*.json` (not `navigation.json`/`redirects.json`), then other pages' frontmatter (a listing card's title or description). It rewrites that whole value (JSON-escaped, or frontmatter-quoted when needed) and returns `where` (`page`/`shared`/`details`/`other`), which the client's saved message explains. It refuses text none of these hold (the design's own words), text held in more than one place, a change across formatting, text repeated without a matching `index`/`count`, and `<`, `>`, backticks, `{{`/`}}` and entity codes. The client matches the frame's path against the preview prefix without its trailing slash, because Next.js redirects the homepage to `…/<signature>`. The frame holds its reload (`key`) while someone is typing, and after a rebuild goes back to the page and scroll position it showed (`ready`/`scroll`/`go` messages).
- The user's own Anthropic key (optional) is in MongoDB (`users.anthropicKey`). It's AES-256-GCM encrypted under `DATA_ENCRYPTION_KEY`, with the user id as associated data. Never send it to the browser (use `getAnthropicKeyHint()`).
- Claude credits (`server/src/credits.js`, `routes/credits.js`, `claude-proxy.js`; client `lib/credits-store.ts` (no React: `site-api.ts` imports it, and server components import that) with its hooks in `lib/credits.ts` (client components only), `CreditBadge.tsx`, `BuyCredits.tsx`, `/credits` with `CreditsOverview.tsx`):
  - **Which key:** every Claude request gets its key from `claudeKeyFor(userId)`, never from `getAnthropicKey` directly. **Own keys are off** (`OWN_KEYS = false` in `credits.js`): everyone uses the app's key through credits, stored keys are ignored, `PUT /api/settings/anthropic-key` returns 403, and `GET /api/settings` sends `ownKeys: false` and no key hint, so the Settings card shows only the model picker. With `OWN_KEYS` on, the account's own key wins and is never charged. Otherwise it's the app's key (`PLATFORM_ANTHROPIC_KEY`, `config.platformAnthropicKey`) while `users.credits.balance` is above zero. Otherwise it throws `ClaudeAccessError`: `anthropic_key_required` (400, no app key) or `credits_exhausted` (402). Routes return `{ error: code, message }`.
  - **Price:** 1 credit = $0.0001 (`CREDITS_PER_USD`), and every account gets `FREE_CREDITS` = 10,000 ($1) once it connects GitHub. `createUser` sets `users.credits` (`balance`, `granted`, `purchased`, `used`) to zero with `freePending: true`; the GitHub callback calls `grantGithubCredits`, which grants once per account and once per GitHub user id (`freeCreditGrants`, `_id` = GitHub id, kept after unlinking; `connectDb` claims the ids of accounts already connected) and redirects with `credits=granted|used`. `creditsView` sends `freePending` and `freeCredits`, and the dashboard steps, Settings → GitHub, `/credits`, the navbar badge and `claudeAccess` point waiting accounts to Connect GitHub. `connectDb` gives the full allowance to accounts from before credits. `creditsFor` prices a request's `usage` from the `PRICES` table (a dated snapshot id such as `claude-haiku-4-5-20251001`, which replies report, is priced as its alias) (input, output, cache read, cache writes at 1.25x/2x, web searches at $0.01). With a refusal fallback, it charges the dearer of the asked-for and the answering model. Unknown models are charged at `UNKNOWN_PRICE`. Keep `PRICES` in step with Anthropic's prices and `CLAUDE_MODELS`.
  - **Metering:** `meterClaude` records each request in `claudeUsage` (tokens, `credits`, `charged`, `kind`, `command`) and, when charged, `$inc`s the balance down. It never throws. Every Claude request (proxy, assistant step, site-update merge) runs through a `Spend` from `beginSpend` (`credits.js`), which refuses to start it unless the balance is above zero, caps its `max_tokens` to what the balance buys down to `-OVERDRAFT` (200 credits) after its estimated input (`maxTokens`; a cached request is priced as a cache write, 2x input for the 1-hour cache, except `cachedTokens` the caller knows are cached: the assistant passes the previous step's size, or `lastPrompt` saved on the conversation when it's under 55 minutes old, so a turn whose input alone would pass the limit is refused before it's sent; with credits still left, `shortfall` makes the assistant say what it would cost and suggest a new conversation), watches it as it streams (`track`: input from `message_start`, output estimated from streamed characters until `message_delta` gives the real count) and charges it (`finish`). All of an account's running requests count against the one limit (`accounts` in `credits.js`), and a request is stopped once they take it to `-OVERDRAFT`. A stopped request keeps what it wrote: the proxy ends the stream as a `max_tokens` reply (`content_block_stop`, `message_delta`, `message_stop`), the assistant keeps the text and ends the turn (`out_of_credits`), and a site-update merge (useless half done) fails with an out-of-credits message. Thinking isn't streamed, so only the `max_tokens` cap bounds it. The template's `edit-page.js` keeps its best result when a follow-up request gets a 402. Each record has a `runId` grouping one job (`issueProxyToken` makes one per token), assistant turn (the turn id) or site update; records from before it have none.
  - **History, merged and split:** `GET /api/credits/history?type=usage` returns one item per run (`usageRunsPipeline` + `usageRun` in `db.js`: a record without `runId` is a run of its own; dated by its latest request, so `before` pages by run): its `credits` merged (what was charged) and `models` split (each with `provider` (`providerOf` in `ai-providers.js`: `deepseek-*`, OpenAI `gpt-*`/`o<n>`, or Claude), requests, tokens and credits). The newest page also has `summary` (`usageByProvider`): the credits used, merged and per provider. `CreditsOverview.tsx` shows the split above the table (`UsageSplit`) and a run per row, dedupes items by id (a running run moves to the top), and the Balance card's "Used" stays `users.credits.used`, one balance for both.
  - **Site scripts never see the app's key:** a copy is a repo its owner can change. On credits, the commands route gives the job a one-off token (`issueProxyToken`) as `ANTHROPIC_API_KEY` and the proxy's URL as `ANTHROPIC_BASE_URL` (`jobEnv(token, model, baseUrl)`), and revokes it when the job ends. `claude-proxy.js` listens on its own loopback port (so Nginx can't reach it) and accepts only `POST /v1/messages`. It checks the token and the balance, caps `max_tokens` (see Metering), forwards with the app's key (plus `anthropic-version`/`anthropic-beta`), streams the reply back one whole event at a time (so it can be ended cleanly at the overdraft limit), and charges what the reply's `message_start`/`message_delta` (or JSON) `usage` says, a stopped reply included. Every version of the site's scripts reads both variables, so no template change is needed. The cheaper fast model goes to its own provider instead: a `deepseek-*` model to DeepSeek's Anthropic-compatible API as it is (`DEEPSEEK_UPSTREAM`, `config.deepseekKey`), an OpenAI one (`gpt-*`) through `openai-bridge.js` (`forwardOpenAI`), which translates the request to OpenAI's Responses API and the reply, streamed or not, back into Claude's message, events, usage (cached input as `cache_read_input_tokens`) and errors, refusing tools, documents and tool turns as invalid requests so the scripts fall back to Claude. Both are charged from `PRICES` (DeepSeek at its peak-hour price, OpenAI with its long-context price past `long.above` input tokens). Jobs on a proxy token get it as `TWINSTACK_FAST_MODEL` (`currentFastModel()` in `fast-model.js`): the admin's choice on `/admin/models` (`GET`/`PUT /api/admin/models`, `appSettings` doc `fastModel`, loaded at startup and kept in memory, one API process) (the page also has a cost explorer, `ModelCostExplorer.tsx`: every card prices a task's tokens, a preset or Custom with sliders; `GET /api/admin/models/usage?days=` gives each card its last 30 days' requests and credits (`usageByModel`) and each section how many sites chose their own models (`siteModelOverrides`)), else `FAST_PAGE_MODEL`, else `deepseek-flash` with `DEEPSEEK_API_KEY`, else `gpt-6-luna` with `OPENAI_API_KEY`; `off`, or a model whose provider has no key, means none. That is the default: each site may choose its own (`siteCopies.fastModel` `{ model, updatedAt, updatedBy }`, `getSiteModels`/`setSiteModel` in `db.js`), on its AI models screen under Advanced (`ModelPanel.tsx`, a dropdown; `GET …/ai-models` returns `{ fast, image }`, `PUT …/ai-models` takes `{ kind: "fast", model }`: `default`, `off` or a model `setFastModel` would take). `fastModelForSite(siteId)` is what the commands route and the site-details turn use: the site's choice while its provider has a key, else `currentFastModel()`. Sites known only by name (old workspace metadata) always get the default. The template's `edit-page.js` uses it for routine page work and falls back from it to `TWINSTACK_MODEL`. With the account's own key, scripts get that key directly, as before.
  - **Task size:** commands with `sized` in `commands.js` (`page-edit`, `page-generate`, `chrome-design`) are measured by `taskSize` in `server/src/task-size.js` before they run, when a fast model is in play: rules only (no request), from the instruction split into clauses, each scored by its verb (remove, change, add, build, redesign…) and what it touches (interactive features, design and layout words, new sections), the request taking its hardest clause. `small` needs every clause recognised as small work (a removal, wording or facts, a one-property tweak, a move), so unknown wording is `standard` (the old behaviour), never `small`. The assistant's `task_size` label (`taskSizeField` in `assistant/tools.js`, passed by `AssistantProvider` as `taskSize`) wins over the rules. The size reaches the script as `TWINSTACK_TASK_SIZE` (`jobEnv`'s fifth argument) and heads the job's log (`describeTaskSize`). A copy whose `edit-page.js` doesn't contain `TWINSTACK_TASK_SIZE` gets no fast model for a complex request. `npm --prefix server run check-task-size` checks the rules against 246 labelled requests and fails on any small/complex swap: run it after changing a rule, and add the request that made you change it.
  - **Provider balances** (`server/src/provider-health.js`, `/admin/providers`, `AdminProviders.tsx`): whether the app's own keys can keep paying. Spend is the charged `claudeUsage` records per provider (`chargedByProvider`, `providerOf`), at the app's `PRICES`; the daily rate is the larger of the last 24 hours and the 7-day average. DeepSeek's balance comes from `GET https://api.deepseek.com/user/balance` (yuan converted at `CNY_PER_USD`); Anthropic and OpenAI don't report one, so an admin enters it (`PUT /api/admin/providers/:provider/balance`, appSettings `providerBalance:<provider>`) and what's recorded since is taken off. Runway = balance left ÷ daily rate; `level` is `low` under `PROVIDER_ALERT_DAYS`. `noteProviderError` (called from `claude-proxy.js`'s `forward`, `openai-bridge.js`'s `sendToOpenAI`, `images.js`, the assistant's `runTurn`, `details-turn.js` and `site-update.js`'s merge, only for the app's keys) records refusals in `providerErrors` (TTL 30 days) by `errorKind` (Anthropic's 400 "credit balance", OpenAI's `insufficient_quota`, DeepSeek's 402 → `balance`; 401/403 → `auth`; 429; 529/503), never a script's bad request, and emails the admins at once for `balance`/`auth`. `startProviderMonitor` (index.js) runs every 15 minutes: low/empty runway emails (`alertOnce`, at most every 12 hours each, remembered in appSettings `providerAlerts`), and once a day after 02:00 UTC `checkProviderCosts` compares the last 3 complete days with Anthropic's `cost_report` (`ANTHROPIC_ADMIN_KEY`, cents as decimal strings; `ANTHROPIC_COST_WORKSPACE_ID`) and OpenAI's `organization/costs` (`OPENAI_ADMIN_KEY`, dollars; `OPENAI_COST_PROJECT_ID`) into `providerCosts`, flagging a day off by more than 5% or 50¢. One API process runs the monitor. The page refreshes every 30 s and also lists the latest purchases (`recentPurchases`). Its "Credits by date" section (`CreditActivity.tsx`, `GET /api/admin/providers/activity?from=&to=&tz=`, `creditActivityReport` → `creditActivity` in `db.js`) gives, for local dates in the admin's time zone (helpers in `server/src/zoned-days.js`, shared with `analytics.js`), credits bought (by `paidAt`; demo apart), free credits given to accounts created then, and charged credits used per provider, per day and per account (top 100 by use, with each balance now), plus their cost at the providers and what buyers paid; at most 366 days.

The client store (`useCredits`) loads once, again on focus and whenever `api()` starts Claude (`STARTS_CLAUDE` in `site-api.ts`, also on a 402), and every 5 s while `active`.

The switch also covers the screens' own AI buttons (`useAutoApply()`, which reads it without the provider's re-renders): on, "Design with the AI", the SEO "Suggest" (then "Write it") and the page editor's change and convert buttons run without `dryRun`, so the script writes and logs the change itself (the page editor keeps a second button to see it first); off, they preview as before. With it on, each message's CHANGES line also tells Claude not to ask permission for what the owner asked (`composeUserMessage`, so no `TOOLSET_VERSION` change).
    - When every proposal of the newest message is settled and an applied one set `continue_after`, the browser sends `{ continue: true }` and Claude carries on (e.g. plan → create pages → write them).
    - Applied changes are logged in the work log as `assistant:<tool>` (`logWork`), except page previews (logged by `applyProposal`), the search writer (logs itself), notes and publishing.
- Dashboard (`/dashboard`, `Dashboard.tsx`): setup steps until the first copy exists (connect GitHub, get approved, create the site, optionally set up Claude), then the copies as cards. The template is never listed; it's the "Create my site" action (`CreateSite.tsx`, which posts to `…/duplicate` with a repo name made by `repoNameFor` in `lib/repos.ts`). Account, GitHub connection and the Anthropic key are on `/settings`.

Route helpers shared by `routes/workspaces.js` and `routes/assistant.js` (`handle`, `keyFor`, `requireJson`) live in `routes/helpers.js`.

**Mutating routes require `Content-Type: application/json`** (415 otherwise). This is the CSRF defence together with the `SameSite=Lax` cookie, so keep it on new POST routes.
