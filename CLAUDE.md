# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js 16 (App Router, React 19, Tailwind 4) frontend in `client/` and an Express 5 API in `server/` (plain ESM JavaScript, no build step). Users have email and password accounts, connect GitHub to them, see the site template and their copies of it, can duplicate a repo (full history) into their own account, and can manage a twinstack-site repo (run its build, content and Claude commands, then commit and open a PR) from the browser. The session cookie only identifies the account. MongoDB (`server/src/db.js`, required at startup) stores accounts (password hash, linked GitHub profile and encrypted token, encrypted Anthropic key) and which repos are copies of the site template. Deployment to a droplet (frontend on `builder.` and API on `api.` subdomains, MongoDB on the same host) is covered in `DEPLOY.md`, and `ecosystem.config.cjs` is the PM2 config. Updates are shipped with `deploy.sh` (see `UPDATING.md`), which `.github/workflows/deploy.yml` runs over SSH after lint and build pass on every push to `master`. It pulls, runs `npm ci`, builds and restarts based on which paths changed (`server/`, `client/`, `ecosystem.config.cjs`), so keep those path rules in sync if the layout changes.

**Before writing any code in `client/`, read `client/AGENTS.md`.** This Next.js version has breaking changes from what you may know; consult `client/node_modules/next/dist/docs/`. For example, route protection lives in `client/src/proxy.ts` (exporting `proxy`), not `middleware.ts`.

## Commands

Node 20.12+ (both packages use `node --env-file-if-exists`).

```bash
npm install          # root; postinstall also installs client/ and server/
npm run dev          # API on :4000 (node --watch) and web on :3000, via concurrently
npm run build        # builds client only (server needs no build)
npm run start        # production start of both

npm --prefix client run lint   # ESLint (eslint-config-next); the only lint in the repo
```

There are no tests. Env setup: copy `server/.env.example` → `server/.env` (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `JWT_SECRET`, `MONGODB_URI` and `DATA_ENCRYPTION_KEY` are required; the server throws at startup without them, and exits if MongoDB is unreachable) and `client/.env.example` → `client/.env.local` (`API_URL`). Optional server vars: `WORKSPACES_DIR` (see the site manager section below), and `PLATFORM_ANTHROPIC_KEY` and `CREDITS_DEMO_PURCHASES` (see Claude credits below).

## Architecture

**Single origin via rewrites.** The browser only ever talks to Next.js on :3000. `client/next.config.ts` rewrites `/auth/*` and `/api/*` to Express, so the httpOnly `session` cookie is first-party. The GitHub OAuth callback URL therefore points at the *client* (`http://localhost:3000/auth/github/callback`), not the API. `API_URL` is read at build time. `experimental.proxyTimeout` is raised to 10 minutes because duplication can take a long time.

**Accounts and session.** Email and password accounts live in `routes/auth.js` (register, login, logout, with an in-memory failed-login limit) and `passwords.js` (scrypt). The cookie is a JWE (`dir` + A256GCM, key derived from `JWT_SECRET`) holding only `{ uid }`. `requireAuth` (`session.js`) loads the account from MongoDB on every request. It sets `req.user` to the `publicUser()` shape (`{ id, email, name, github | null }`, where `id` is the ObjectId hex) and `req.githubAuth` to the decrypted GitHub token or null. Use `requireGithub` after it on any route that talks to GitHub. Workspace keys, job ownership, Anthropic keys and `siteCopies.userId` all use the account id, never the GitHub id.

**Who verifies the session.** Only Express can decrypt the cookie. `client/src/proxy.ts` only checks that the cookie *exists* on `/dashboard/*`, `/sites/*`, `/settings/*` and `/credits/*`, and sends guests to `/login?next=…`. `?next` must go through `lib/safe-next.ts`. Server components call `getUser()` in `client/src/lib/session.ts` (`server-only`), which forwards the cookie to `GET /api/me`. Client components (`Dashboard`, `CreateSite`) call `/api/*` directly from the browser through the rewrite.

**GitHub connection and token refresh.** `/auth/github` → `/auth/github/callback` links GitHub to the logged-in account (`linkGithub`, one GitHub account per app account), and errors redirect to `/dashboard?github_error=…`. `getAccessToken(req)` in `server/src/github.js` refreshes the token when it's within 60s of expiry (only when the OAuth App issues expiring tokens) and saves it back to MongoDB. Any route that calls GitHub should get its token through this function. Any GitHub 401 or refresh failure throws `ReauthRequiredError`, which routes map to `401 { error: "reauth_required" }`. The client treats that code as "Reconnect GitHub" (a link to `/auth/github`).

**Scopes.** `read:user user:email repo workflow`, requested in `server/src/routes/auth.js`. `workflow` is needed to push repos that contain `.github/workflows/*`. The duplicate route rejects older GitHub connections that lack it with a `reauth_required` response.

**Duplication** (`server/src/duplicate.js`). It validates owner and name, then `POST /user/repos`. Next it runs `git clone --bare` of the source into a temp dir and pushes `refs/heads/*` and `refs/tags/*` to the new repo. After that it PATCHes the default branch to match the source, and finally removes the temp dir. If the name already exists and that repo is empty and admin-owned, it is reused, which lets a failed copy be retried. A non-empty repo is never overwritten. The token reaches git only through `GIT_CONFIG_*` env vars (an `http.extraheader`), never through argv or a remote URL; keep it that way. The server host needs `git` installed. Error classes: `DuplicateError` has a user-safe message and HTTP status. `MissingScopeError` maps to reauth. Anything else becomes a 502, with `err.partialRepo` noted if an empty repo was left behind.

**Site manager** (`/sites/[owner]/[repo]`, the README has the user-facing summary). It drives a twinstack-site repo's scripts from the browser:
- `server/src/workspace.js` keeps a persistent clone per user and repo at `WORKSPACES_DIR/<userId>/<owner>/<repo>`. Repo metadata and the `npm ci` lockfile stamp live inside `.git/` so they never appear as changes. It also handles status, diff, discard, commit/push/PR and reset. A per-workspace lock (`acquire`) makes sure only one command or git operation touches a clone at a time.
- `server/src/commands.js` is the only list of runnable commands. Each builds a fixed `node scripts/<x>.js` argv from validated input. There is no shell, and values that start with `-` are rejected. New site commands go here. Scripts get the `jobEnv()` allowlist, never `process.env`, so the GitHub token and server secrets can't reach repo code.
- `server/src/jobs.js` runs commands in memory. The client polls `GET /api/jobs/:id?since=<offset>` (not SSE, so it works through the Next rewrite proxy). Jobs are lost on restart.
- `server/src/site-files.js` reads site data (collections, pages, nav) by parsing files. **Never import repo code into the server process.**
- `server/src/routes/preview.js` serves `dist/` under a signed URL with a CSP sandbox header, and rewrites root-relative `href`/`src`/`url()` into the preview prefix. The client iframe is sandboxed without `allow-same-origin`, so keep both.
- The user's own Anthropic key (optional) is in MongoDB (`users.anthropicKey`). It's AES-256-GCM encrypted under `DATA_ENCRYPTION_KEY`, with the user id as associated data. Never send it to the browser (use `getAnthropicKeyHint()`).
- Claude credits (`server/src/credits.js`, `routes/credits.js`, `claude-proxy.js`; client `lib/credits-store.ts` (no React: `site-api.ts` imports it, and server components import that) with its hooks in `lib/credits.ts` (client components only), `CreditBadge.tsx`, `BuyCredits.tsx`, `/credits` with `CreditsOverview.tsx`):
  - **Which key:** every Claude request gets its key from `claudeKeyFor(userId)`, never from `getAnthropicKey` directly. **Own keys are off** (`OWN_KEYS = false` in `credits.js`): everyone uses the app's key through credits, stored keys are ignored, `PUT /api/settings/anthropic-key` returns 403, and `GET /api/settings` sends `ownKeys: false` and no key hint, so the Settings card shows only the model picker. With `OWN_KEYS` on, the account's own key wins and is never charged. Otherwise it's the app's key (`PLATFORM_ANTHROPIC_KEY`, `config.platformAnthropicKey`) while `users.credits.balance` is above zero. Otherwise it throws `ClaudeAccessError`: `anthropic_key_required` (400, no app key) or `credits_exhausted` (402). Routes return `{ error: code, message }`.
  - **Price:** 1 credit = $0.0001 (`CREDITS_PER_USD`), and every account starts with `FREE_CREDITS` = 10,000 ($1). `createUser` sets `users.credits` (`balance`, `granted`, `purchased`, `used`), and `connectDb` backfills older accounts. `creditsFor` prices a request's `usage` from the `PRICES` table (a dated snapshot id such as `claude-haiku-4-5-20251001`, which replies report, is priced as its alias) (input, output, cache read, cache writes at 1.25x/2x, web searches at $0.01). With a refusal fallback, it charges the dearer of the asked-for and the answering model. Unknown models are charged at `UNKNOWN_PRICE`. Keep `PRICES` in step with Anthropic's prices and `CLAUDE_MODELS`.
  - **Metering:** `meterClaude` records each request in `claudeUsage` (tokens, `credits`, `charged`, `kind`, `command`) and, when charged, `$inc`s the balance down. It never throws. Only the start of a request is refused, so the balance can end slightly below zero. The assistant meters each request of a turn as it finishes (`onMessage` in `runTurn`) and stops between requests once the balance is gone (`canContinue`). The site update meters `mergeWithClaude` (`onUsage`). Each record has a `runId` grouping one job (`issueProxyToken` makes one per token), assistant turn (the turn id) or site update; records from before it have none.
  - **History, merged and split:** `GET /api/credits/history?type=usage` returns one item per run (`usageRunsPipeline` + `usageRun` in `db.js`: a record without `runId` is a run of its own; dated by its latest request, so `before` pages by run): its `credits` merged (what was charged) and `models` split (each with `provider` (`providerOf`: `deepseek-*` or Claude), requests, tokens and credits). The newest page also has `summary` (`usageByProvider`): the credits used, merged and per provider. `CreditsOverview.tsx` shows the split above the table (`UsageSplit`) and a run per row, dedupes items by id (a running run moves to the top), and the Balance card's "Used" stays `users.credits.used`, one balance for both.
  - **Site scripts never see the app's key:** a copy is a repo its owner can change. On credits, the commands route gives the job a one-off token (`issueProxyToken`) as `ANTHROPIC_API_KEY` and the proxy's URL as `ANTHROPIC_BASE_URL` (`jobEnv(token, model, baseUrl)`), and revokes it when the job ends. `claude-proxy.js` listens on its own loopback port (so Nginx can't reach it) and accepts only `POST /v1/messages`. It checks the token and the balance, forwards with the app's key (plus `anthropic-version`/`anthropic-beta`), streams the reply back, and charges what the reply's `message_start`/`message_delta` (or JSON) `usage` says, a stopped reply included. Every version of the site's scripts reads both variables, so no template change is needed. A `deepseek-*` model is sent to DeepSeek instead (`DEEPSEEK_UPSTREAM`, `config.deepseekKey`) and charged from `PRICES` at its peak-hour price: with `DEEPSEEK_API_KEY` set, jobs on a proxy token get `TWINSTACK_FAST_MODEL` (`config.fastPageModel`; `FAST_PAGE_MODEL=off` turns it off), which the template's `edit-page.js` uses for routine page work and falls back from to `TWINSTACK_MODEL`. With the account's own key, scripts get that key directly, as before.
  - **Live balance:** `beginClaudeActivity` marks the account busy while an assistant turn, a Claude command or a site update runs, and `GET /api/credits` (`creditsView`) reports it as `active`. The client store (`useCredits`) loads once, again on focus and whenever `api()` starts Claude (`STARTS_CLAUDE` in `site-api.ts`, also on a 402), and every 5 s while `active`.
  - **Buying:** `POST /api/credits/purchases` `{ credits }` takes multiples of `PURCHASE_STEP` (1,000) up to `MAX_PURCHASE`. For now it's a demo (`CREDITS_DEMO_PURCHASES`, on unless `false`): `addPurchasedCredits` records a paid `creditPurchases` document with `provider: "demo"` and adds the credits at once. A payment provider would create it as pending and add the credits from its webhook. `GET /api/credits/history?type=usage|purchases&before=&limit=` returns the history a page at a time, newest first.
- The account's Claude model is `users.claudeModel`, chosen on `/settings#claude` (`ModelPicker` in `AnthropicKey.tsx`; `GET /api/settings` returns `model` and `models`, `PUT /api/settings/model` saves). The list is `CLAUDE_MODELS` in `server/src/claude-models.js`; `getClaudeModel()` falls back to `DEFAULT_MODEL` (`ASSISTANT_MODEL` env if it's in the list, else `claude-opus-5-5`) when none is chosen or the stored one is no longer offered. Claude commands get it as `TWINSTACK_MODEL` through `jobEnv(anthropicKey, model, baseUrl)`. The assistant has its own choice, `users.assistantModel` (`getAssistantModel()`, default `DEFAULT_ASSISTANT_MODEL`: `ASSISTANT_CHAT_MODEL` env if listed, else `claude-sonnet-5-5`, because it mostly reads and plans while the page writer designs), sent as `assistantModel` and saved with `PUT /api/settings/assistant-model`; `AnthropicKey.tsx` shows a second `ModelPicker` for it when the server sends it, and `runTurn` gets it. Only offer models that accept the assistant's request as it is (adaptive thinking, effort, `fallbacks: "default"`).
- Site scope (`server/src/sites.js`): `/api/repos` returns only the template (`SITE_TEMPLATE_REPO`) and copies of it, each with a `role`. Duplicating is allowed only from the template. Workspaces refuse the template (in `keyFor` and `openWorkspace`) and anything that isn't a copy. A copy is only a `siteCopies` record (by repo id), written by Duplicate, never a repo that is merely named like one. That record is the access control: opening a site runs its scripts on the server, duplicating needs read access to the (private) template on GitHub, and `openWorkspace` also requires push access to the copy. There is no separate allowlist. `server/scripts/record-copies.js` (`npm --prefix server run record-copies -- owner/repo`) records copies made before Duplicate recorded them.
- Claude page edits: the `page-edit` command only takes `content/**/*.md` pages, plus up to 6 images (`assets/img/…` paths or http(s) URLs) passed as `--image=`. A preview runs with `--dry-run --proposal-out=.git/twinstack-proposal.json`. The command's `prepare` hook deletes any older proposal first, so a failed preview never shows a stale one. `site-files.js` reads, applies and clears the proposal. Applying writes the user's (possibly edited) text and doesn't call Claude. Uploads (`POST …/uploads`, base64 JSON, 5 MB, file type checked from the bytes) are saved to `assets/img/uploads/`. That route parses its own 8 MB JSON body: `index.js` skips the global 100 KB parser for it, and Nginx needs `client_max_body_size` raised (see DEPLOY.md). `overview.features.pageEditImages` is false for copies whose `edit-page.js` predates `--proposal-out`, and the UI then hides images and the preview pane.
- Claude edits of other markdown (`MarkdownEditor` in `EditPanel.tsx`, not offered in the UI at the moment): the `md-edit` command runs the copy's `scripts/edit-md.js <file> <instruction>`, with `--dry-run --proposal-out=` for a preview. It takes files that pass `isEditableMarkdown` in `site-files.js`: `.md` outside `content/`, `dist/`, `node_modules/`, `static/` and dot-directories, and not `CHANGELOG.md`. The overview lists them as `markdownFiles`. Their proposals have `mode: "markdown"`, and `applyProposal` checks the file against `isEditableMarkdown` instead of the `content/` pattern. `overview.features.mdEdit` is false for copies without `scripts/edit-md.js`, and the mode then offers to add it: `POST …/install/md-edit` reads `MD_EDIT_FILES` (`scripts/edit-md.js`, `scripts/lib/schedule-jobs.js`) from the template's default branch on GitHub (`readRepoFile` in `github.js`, with the user's token), and `installMdEdit` writes the ones the copy lacks and adds the `md:edit` npm scripts. It never replaces an existing file, and the result is an ordinary uncommitted change. It fails with 409 until those files are pushed to the template.
- Publishing (`server/src/publishing.js`; `usePublishing` in `site-hooks.ts`, shown on the Home screen and the Publish screen): each copy deploys itself with its own `.github/workflows/deploy.yml` on every push to its default branch, to GitHub Pages at `https://<owner>.github.io/<repo>/`. Duplicate turns Pages on with GitHub Actions as the source (`enablePages`, failures only logged). `GET …/publishing` reports the Pages URL, the latest deploy run on the default branch and `workflowReady` (the pushed `deploy.yml` contains `BASE_PATH`). `POST …/publishing/enable` turns Pages on, `…/publishing/deploy` dispatches the workflow, and `POST …/install/publishing` copies `PUBLISHING_FILES` from the template into older copies as uncommitted changes (`updateFromTemplate`). It polls every 8 s while a deploy runs or for 90 s after the workspace changes, and every minute otherwise. Pages on a private repo needs a paid GitHub plan, and GitHub's refusal is shown as is. Custom domains (`DomainSettings.tsx`, DNS records from `client/src/lib/custom-domain.ts`): `PUT …/publishing/domain` (`normalizeDomain`, then `setDomain`) saves the Pages `cname` (null removes it) and redeploys when the pushed workflow is ready, because the workflow reads the domain back from `configure-pages` and builds without the `/<repo>` prefix. `PUT …/publishing/https` toggles `https_enforced` (GitHub refuses until the certificate exists), and `GET …/publishing/domain-check` returns GitHub's `pages/health` (202 → `pending`). The README has the user-facing DNS steps.
- Work log: copies with `scripts/lib/knowledge.js` send `knowledge/notes.md` and a work log to Claude on every request. Each entry is a line (`- <date> · <command> · <file> · <instruction>`) followed by up to 5 indented `  - ` summary points (at most 200 characters each), which Claude wrote about what the change did. Entries from before summaries are just the line.
  - **One string everywhere:** an entry is kept as a single string with its newlines in MongoDB, `workLogForgotten`, the memory API and the tab. In `site-files.js`, `segmentsOf`/`entriesOf` group a file's lines into entries, and `isWellFormedEntry` validates them.
  - **Rewriting and rotation:** `rewriteCommittedWorkLog` and the rotation in `appendCommittedWorkLog` work on whole entries, so a summary never ends up separated from its line.
  - **Applied previews:** a preview's proposal carries the summary (`summary`, cleaned by `cleanSummary` in `readProposal`). The preview pane shows it, and `applyProposal` logs it with the entry. Applying never calls Claude.
  - **Memory tab:** shows each entry's points, and **Edit** changes the instruction and the summary (one point per line). `replaceMemoryLine` rejects a bad first line or more than 5 points.

  The rest of the work log works as follows. The committed `knowledge/work-log.md` only holds the checked-out branch's lines, so after a change goes out as a PR and `resetToDefault` runs, its line would be missing until the PR merges. So the log is also kept in MongoDB (`workLog`, `siteId` = GitHub repo id, recorded in the workspace meta and read with `siteIdFor`), shared by every user of the site. Commands marked `claude: true` in `commands.js` get `prepareWorkLog` before they start: it writes the newest 60 lines of the committed log and the database's, merged, to `.git/twinstack-work-log.md` and passes that path as `TWINSTACK_WORK_LOG`. The script reads the log from there and appends its own lines to it. `collectWorkLog` saves those lines when the job ends, before the lock is released (`startJob` awaits `release`). It keeps only well-formed lines (`- YYYY-MM-DD · …`, at most 600 characters, 100 per run), because the copy's own script wrote them. When merging, the database's order wins, and lines only in the committed log are placed by date after that day's database lines.
- Claude memory tab (`MemoryPanel.tsx`): edits `knowledge/notes.md` through the data-file endpoints (`knowledge-notes` in `DATA_FILES`) and lists the merged work log (`GET …/memory`, `readMemory`), newest first, marking lines older than the 60 that are sent. `POST …/memory/forget` `{ line }`, `…/memory/replace` `{ line, replacement }` and `…/memory/clear` change the database and the checkout's committed log (an ordinary uncommitted change) under the workspace lock, and return the memory plus `status`. Lines are identified by their text. Removed and replaced wording is recorded in the `workLogForgotten` collection, so `mergedWorkLog` drops it even when another branch's committed log still has it. A line written again (`addWorkLogLines`) is un-forgotten. A replacement must stay well-formed: the UI only edits the instruction part. `overview.features.memory` is false for copies without `scripts/lib/knowledge.js`, and the tab then explains why. `applyProposal` logs through `logAppliedChange`, both to the committed file (rotating all but the newest 30 of 60+ entries into `knowledge/archive/`) and to the database. Keep the format and limits in step with the template's `scripts/lib/knowledge.js`. Copies without that file get none of this, and a failed log write never fails the edit.
- Page preview of a proposal (`PagePreview` in `ProposalReview`, between the diff and Apply; not for `markdown` proposals): it builds by itself once per new proposal (a failed build isn't retried), and "Update the preview" rebuilds with the user's edits. Copies without support get a notice whose button runs `POST …/install/publishing` (PUBLISHING_FILES carry the new `build.js`). The `proposal-preview` command's `prepare` (`prepareProposalPreview`) copies the pending proposal to `.git/twinstack-proposal-preview.json`, with `content` replaced by the user's edited text when the client sends it (only when edited, because the global JSON limit is 100 KB), and the step runs the copy's `build.js --proposal=<that> --out=.git/twinstack-proposal-site`. `readProposal` returns `preview` (`url`, `edited`, `builtAt`) only when the build's `.proposal.json` names this proposal's file and `createdAt`; `clearProposal` (discard, apply, a new run) removes the build. The preview router serves it under a second signature: `previewPath(key, kind)` and `verifyPreviewSignature` (which returns the kind) map `site` to `dist/` (its signature unchanged) and `proposal` to `PREVIEW_ROOTS.proposal`, and never serve dot-files. The iframe has the Build tab's sandbox, with desktop and phone widths. `overview.features.proposalPreview` is the literal `--proposal=` in the copy's `build.js`.
- Live diffs: `readProposal` returns the file's current text as `original`, and `LiveDiff.tsx` (using `lib/line-diff.ts`) shows the changes as the user types, next to the proposal in `ProposalReview`, under the draft in `DraftEditor` (against the last save) and under the site tree in `TreePanel`.
- Claude page generation ("Write it yourself", the default mode of the page editor's Content tab): the user writes the page's markdown by hand (`GET`/`PUT …/pages/source`, `readPage`/`savePage` in `site-files.js`), then the `page-generate` command runs `edit-page.js <page> --generate [direction]` with the same `--image`/preview flags as `page-edit`. The site script finds the images in the draft itself. A save must send the `version` (a content hash) it was loaded with, and it is refused with 409 if the file changed in the meantime (a Claude run rewrote it, say). Proposals carry `mode` (`edit`/`generate`) and `warnings` (non-blocking) next to `problems` (the checks the script would have refused to write on). Older copies' proposals have neither, and `readProposal` defaults them. `overview.features.pageGenerate` is false for copies whose `edit-page.js` predates `--generate`: the editor still saves, but the Claude buttons are off. Client: `DraftEditor.tsx` (editor, image insertion at the cursor, never inside the frontmatter), `ProposalReview.tsx` (shared by both modes), `ImagePicker.tsx`. Overview pages carry `url` from their frontmatter, and `isHomePage` in `lib/site-api.ts` (the page at `/`; `content/pages/home.md` only from a server too old to send `url`) puts the homepage first in the Pages list with a badge. The draft editor shows the frontmatter in a separate folded "Page settings (technical)" box and joins the two on save. `SiteManager` keeps the Pages screen mounted once opened, and it tracks unsaved draft edits (`setUnsavedDraft`/`confirmDiscardDraft` in the context), so switching screens never loses a draft and leaving the page or opening another page asks first.
- Header and footer, on the Design screen (`HeaderFooterPanel.tsx`, `HeaderFooterPreview.tsx`, helpers in `header-footer.ts`; `server/src/navigation.js`): `GET …/navigation` returns `content/data/navigation.json` (header `items` and `cta`, `footer` columns, `legal`, and `appearance` with defaults filled in), `supportsAppearance` (the copy's `header.html` and `footer.html` contain `nav.appearance` and `scripts/lib/content.js` contains `navAppearance`), a content `version`, the collections, every page with its built URL (`sitePages`, mirroring the site's slug and `urlPattern` rules; drafts marked) and the footer's tagline and contact details for the preview. `PUT …/navigation` `{ navigation, version }` (`saveNavigation`) refuses a stale version with 409, validates every entry (labels, links that start with `/`, `#`, `mailto:`, `tel:` or `http(s)://`, collections that exist, limits, appearance enums, the `LIMITS` the client mirrors), keeps unknown plain-value fields, the file's other keys, key order and line endings, and writes `appearance` only when sent (the client omits it for copies without support). An unchanged save is byte-identical. The client flags links the build would drop (`linkStatus`, mirroring the site's `linkTarget`) and strikes them through in the preview, which is an approximation in the template's header and footer colours (zinc greys and the `brand` accent); clicking part of it opens that entry. The Design screen stays mounted once opened (`designOpened`), so unsaved edits survive tab switches. `POST …/install/header-footer` copies `HEADER_FOOTER_FILES` (both partials and `content.js`) from the template with `updateFromTemplate`, refusing with 409 until the template has them. "Add a new section" still runs `nav-add` (which scaffolds a new collection); `nav-remove` is no longer offered, because removing an entry in the editor leaves the collection alone. `brand.js` treats a header with `nav.appearance.header.logo` as supporting the logo too.
- Claude-designed header and footer (`ClaudeDesign` in `HeaderFooterPanel.tsx`, shown when `overview.features.chromeDesign`): the `chrome-design` command runs `edit-page.js --chrome [direction]` (always as a preview), and `<ProposalReview chrome />` shows the result built on the homepage before Keep or Throw away. `ProposalReview` without `chrome` (the page editor) never shows a `mode: "chrome"` proposal, and with it shows nothing else. Once the partials carry `data-designed="claude"` (`navigation.designed`), the header's colour, menu position and sticky switches and the footer's colour are hidden: the look is Claude's, while the menu, button, logo, copyright and the tagline/contact switches still apply. - Site updates (`server/src/site-update.js`; `useSiteUpdate` in `site-hooks.ts`, `SiteUpdateCard` in `HomePanel.tsx`, also on Build tools): one click installs the template's newest commit on its default branch (every push to the template is an update; no versions or tags) into the copy's published site, keeping the owner's work.
  - **Routes:** `GET …/site-update` reads the template's latest 50 commits (`GET /repos/<template>/commits`, cached 60 s) and finds the newest one in the copy's published history (`git merge-base --is-ancestor`; a commit the copy never had isn't in its object store, so the check fails).
